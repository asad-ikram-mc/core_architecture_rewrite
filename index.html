1 · The 30-second summary

CORE is the daily ETL that takes Amazon's global social media data out of Sprinklr, cleans and tags it, computes benchmarks against historical performance, and pushes it into a PostgreSQL database that Tableau reads. It covers Facebook, Instagram (feed and Stories), X/Twitter, LinkedIn, YouTube, TikTok, Threads and LINE, across Organic / Boosted / Paid delivery, for accounts worldwide.

Two facts explain most of the pipeline's behaviour:

  1. Each Sprinklr pull is a rolling ~88-day window, not a daily delta. Every pull re-delivers the same posts with refreshed metrics — roughly 20,500 rows a day. A missed day therefore loses metric snapshots, not posts: the next successful pull still contains everything published in the window.
  2. The database only moves on Mondays. Non-Monday runs accumulate into master_table.csv and stop there. Everything from stage 3b onwards is gated behind a Monday check — and that check reads the pulldate, not today's date, so a replay of a Monday behaves like a Monday whenever it is run.

The pipeline is 15 deployed Lambda functions plus one Fargate task. The Lambdas run in eu-north-1 (Stockholm); the Fargate cluster and the RDS database are in eu-west-2 (London). That split is deliberate, and λ3 pins its ECS client to eu-west-2 accordingly.

2 · Infrastructure & storage

There are two S3 buckets and one database.

amazon-global-gsmc-sprinklr — the raw landing zone. Sprinklr drops files here every morning into dated folders. RAWDATA/Fluency-Monthly/ holds the daily organic pull (11 files), RAWDATA/Fluency-Weekly/ the weekly paid and follower pull (5 files), RAWDATA/Tag-Pull/ the tag pull (4 files) and RAWDATA/Fluency-Tags-Only-Pull/ the tags-only pull (3 files) — 23 files in total, which is the number λ1 validates. The bucket also holds copy_production_data/RAWDATA/, a pristine mirror taken before any column renaming, and mapping_column_json/COLUMN_MAPPINGS_sprinklr.json.

The single most-missed operational fact: the column mapping is read from S3, not from the repository. Merging a mapping fix to main changes nothing until the JSON is uploaded to s3://amazon-global-gsmc-sprinklr/mapping_column_json/.

wikitablescrapexample — the working and curated layer. Validated files land under amazon_sprinklr_pull/fluency/ and amazon_sprinklr_pull/Fluency-Weekly/. The heart of the pipeline is amazon_sprinklr_pull/result/master_table.csv, the accumulator every daily run merges into. Stage outputs sit in weeklybackup/, monthlybackeup/ (the typo is real and load-bearing), for_tagging/, finalmaster/ and tableau_layer/. Two prefixes live at the bucket root, not under amazon_sprinklr_pull/: filtered_posts/ (the audit trail) and check/ (the pre-push snapshots).

The database is RDS PostgreSQL sprinklrproddb in eu-west-2. The pipeline writes seven tables, of which sprinklr_table is the one Tableau reads. The others are sprinklr_lookup_check, follower_table, blacklist_table, is_branded_true_table, permalink_registry and comment_sentiment_history.

3 · Stage 1 — Validation (λ1 · Data_validation)

λ1 is the gate. It runs on a schedule, ignores its event payload entirely, and works only on today's folder — the date comparison is a hard equality, so there is no way to ask it for an older date. (That is what lambda_1b.py exists for: a local-only copy that accepts a target_date. It is deliberately excluded from CI deployment.)

The sequence is: back up all four raw folders to copy_production_data/ first, then validate. Validation compares each file's column set against a hardcoded expected_file_structure dictionary — 23 entries, exact set comparison. If a file validates and the mapping JSON contains renames for it, λ1 rewrites the file in place in the raw bucket, which is why the untouched copy_production_data/ mirror matters so much.

On a clean run λ1 invokes λ2a. If the tag folders are missing or incomplete it invokes λ2b instead. It never invokes both.

Why a five-day outage went unnoticed: λ1 returns statusCode 200 even when it rejects every file, and reports problems only by SES email — never to Slack. Nothing watching exit codes can tell a rejected day from a good one. A single unrecognised column blocks the entire day, not just the offending file.

4 · Stage 2 — The movers (λ2a / λ2b)

Both movers copy the four validated folders from the raw bucket into the curated bucket, and both end by writing done.txt sentinel files that trigger the next stage. On Mondays they also copy the follower file to amazon_sprinklr_pull/follower/.

λ2a is the happy path. It copies folders verbatim, preserving the original dated folder name, writes the tag done.txt immediately, writes a timestamped marker under post_id_mapping/trigger_post_id_backup/ that fires λ2c, then sleeps for 240 seconds before writing the daily done.txt that starts the merge. That sleep is the pipeline's only sequencing mechanism between the tag stage and the merge.

λ2b is the recovery path. It does the same move but with a three-level fallback for tag folders — today's folder, else the latest folder, else the copy_production_data/ backup — and it validates and column-maps the seven tag files itself before writing them to a {today}_processed/ folder. It alerts by SES on any exception.

Two asymmetries worth knowing. λ2b never writes the trigger_post_id_backup/ marker, so the post-ID lookup refresh (λ2c) is silently skipped on every recovery-path day. And λ2b's fallback can serve a stale day's tag data without any warning, because there is no success email at all.

5 · Stage 2c / 2d — Lookups & tag assembly

λ2c (get_sprinklr_postid) maintains the durable permalink ↔ post_id mapping. It reads exactly two files — PostIDLookup_15_FluencyMonthly.json and PostIDLookup_15_FluencyWeekly.json — and maintains all_mappings.csv plus two lookup files, lookup_by_postid.csv and lookup_by_permalink.csv, all under amazon_sprinklr_pull/post_id_mapping/. The is_current flag simply marks the most recent permalink seen for a given post_id; permalinks are only ever added, never removed. Note that λ2c does no platform-specific URL parsing — no Instagram shortcode decoding, no Facebook fbid handling. That logic lives in λ10.

λ2d (get_latest_tag_file) assembles the tag files the tagging stage will use. It reads from the curated bucket (the copies λ2a/2b just made, not the raw drop) and produces four artefacts under amazon_sprinklr_pull/latest_tag_mapping/: Organic_Tags_12_TagPull.json (a concatenation of the tags-only and monthly organic files — not a rename), Paid_Tags_15_TagPull.json (a merge of the two paid tag files), Target_Geography_17_TagPull.json, and pull_date.txt. The output numbering deliberately differs from the input numbering.

Latent bug: λ2d invokes the downstream prod_push_latest_tag_core function when weekday() in (1, 5). The comment says "Tuesday or Friday", but in Python weekday 5 is Saturday — Friday is 4. The push therefore runs Tuesday and Saturday.

6 · Stage 3 — The merge (λ3 + Fargate)

λ3 itself is an 81-line trigger. It extracts the pulldate from the S3 key that woke it and calls ecs.run_task, passing the pulldate as a container environment variable. The real work happens in the Fargate task task-old-lambda-3, which moved off Lambda because the merge exceeded Lambda's 10 GB memory ceiling.

The task requires all nine organic files to be present for the pulldate or it refuses to run. It loads each into a DataFrame, concatenates them, and — on Mondays only — additionally merges the paid data, joining it to an objective mapping and computing Paid_Reach from per-country reach factors. It then reads the entire existing master_table.csv, concatenates, and de-duplicates across all 182 non-row_number columns keeping the last occurrence.

On Mondays it also writes the filtered snapshot amazon_sprinklr_pull/weeklybackup/backupmaster_<date>.csv, applying a retention window of 45 days for organic and 2 days for paid. Finally it overwrites master_table.csv in place. Success and failure are posted to Slack #amazon-core-alerts — by the Fargate task, not by λ3, which is fire-and-forget and never learns the outcome.

Reading the silence: because the task posts Python exceptions to Slack, a run that produces no Slack message at all is almost certainly a kernel OOM kill rather than a code error. That is the signature of the 27 July incident.

7 · Stage 3b — Post-ID resolution

Triggered by the Monday backupmaster upload, λ3b reads that snapshot (not master_table.csv), adds a post_id column by looking each permalink up in post_id_mapping/lookup_by_permalink.csv, and rewrites permalinks that have since changed to their current form. It writes amazon_sprinklr_pull/monthlybackeup/mapped_data_<date>.csv, where the date is the maximum Pull Date in the data, not the run date, plus a change report under permalink_changes/. It has no day-of-week gate of its own — it is Monday-only purely because its input only appears on Mondays.

8 · Stage 4 — Filtering (λ4 · amazon_sprinklr_paidorganicmainmaster)

λ4 turns the merged raw data into one clean row per post. It maps accounts to countries via countrymapping.xlsx, classifies platform via platformmapping.xlsx and twitter_mapping.xlsx, rolls dozens of platform-specific metric columns up into unified metrics (Impressions, Reach, Engagements, Likes, Shares, Comments, Video Views, Completion Rate, Sentiment), classifies each row as Organic / Boosted / Paid, reconciles paid against organic rows for the same post, and applies filter rules 1 through 6.

Its output is amazon_sprinklr_pull/for_tagging/final_need_to_tagg_{minPullDate}_{maxPullDate}.csv — note the filename carries a date range, not a single date — and its audit trail is filtered_posts/lambda_4_<date>.csv. The column it produces is called Platform; the rename to Platform Granular happens later, in λ7.

9 · Stage 5 — Tagging (λ5 · amazon_paid_organic_tagging)

λ5 is where the business logic lives. It joins the Sprinklr tag pulls onto the metric rows and builds roughly 28 tag columns. Matching happens in three tiers: first on permalink, then for anything unmatched on post_id, and finally — for Facebook only — by post text and account, confirmed through the Apify URL-to-ID service so that two different URL forms of the same post are only merged when they resolve to the same canonical ID. Anything still unmatched falls back to Global.

The notable outputs are Post Format (from the client's format tag, normalised through a mapping agreed in July 2026, then overridden per platform — YouTube becomes Video, Instagram Story becomes Instagram Story, paid rows with no format become Dark); Editorial Format Pillar and Type, where Type is pillar-gated and filtered against an approved-value list so an unrecognised value is silently dropped rather than carried through; and Reputational Topic and Sub-Topic, where the sub-topic is assembled from nine EU5 columns treated as a set.

λ5 also blends in the collab tracker (core_manual_tracker/processed_data.csv) and the LINE tracker (core_line_tracker/processed_line_data.csv), applies geography from the targeted-geography tag file, and enforces rules 7 and 8. Output: amazon_sprinklr_pull/finalmaster/cleaned_master_tab_{min}_{max}.csv.

The collab tracker read has no local error handling, so if λ8 has not finished writing processed_data.csv the run fails. The LINE read is wrapped in a try/except and simply continues with no LINE data — there is no fallback to last week's file.

10 · Stage 6 — Benchmarks (λ6 · amazon_sprinklr_setbenchmark)

λ6 scores every post against pre-computed benchmark tables. It does not calculate the benchmarks — the four workbooks in mappingandbenchmark/ are maintained outside this pipeline; λ6 only computes each post's variance against them.

Organic and Boosted rows are matched on a key of Country + Platform + Delivery + Quarter, lowercased. Boosted always uses the annual bucket. For organic, if the matched quarter has fewer than 10 posts the code falls back to the annual benchmark — a fallback computed in memory that is never persisted, which is why it cannot be audited downstream. Paid rows use a separate key built from country and objective.

Performance metrics produce a proportional variance; rate metrics produce a basis-point difference (10,000 ×). Rules 9 and 10 apply here. Critically, λ6 emits every row twice — once with Benchmark Type = Median and once with Average — so from this point on the row count is double the post count, and any downstream count must account for it.

11 · Stage 7 — Database push (λ7 · tableau_push)

λ7 is the terminal stage. It translates post text (skipping AU/US/UK), attaches comment sentiment, applies rules 11 through 22, aligns columns to the live database schema, and upserts.

The upsert key is post_id_key. For Sprinklr rows it is built from the post_id — falling back to the permalink when no post_id exists — plus the benchmark type and a PAID/NONPAID suffix. For manual and LINE rows it is the RowID plus benchmark type. Because it is an upsert, only the latest state of each post lands in the database, and nothing is ever deleted by λ7 — rows that age out of the rolling window remain in sprinklr_table permanently.

λ7 also writes the pre-push snapshot check/finalsql_<date>.csv, runs four duplicate-detection queries and emails the report if anything is found, and appends removed rows to blacklist_table and is_branded_true_table.

Rule numbering is not execution order: rule 21 runs first in λ7, before rule 11.

12 · Side pipelines (λ8 / λ9 / λ10 / λ11)

λ8 (core_manual_upload_tracker) ingests the hand-keyed collaborator trackers — a legacy combined sheet for pre-2026 posts plus eight per-country sheets (DE, ES, FR, IN, IT, JP, UK, US). It backs up sprinklr_table, deletes every is_manual_tracker = 1 row, reads and normalises the sheets, resolves conflicts against Sprinklr rows using a four-level priority ladder, and writes processed_data.csv. It also deletes losing Sprinklr rows from the database by RowID.

λ8 deletes before it reads, and it never re-inserts. The collab rows return to the database only when λ5 → λ6 → λ7 next run. A crash between the delete and the write therefore leaves Tableau with no collab data until the following Monday chain completes.

λ9 (line_manual_tracker) handles Japan's LINE data, which is not in Sprinklr at all. It reads two tabs of a Google Sheet, repairs post IDs that the sheet has rendered in scientific notation, aggregates the one-row-per-day source into one row per post, tags everything is_manual_tracker = 2, and writes processed_line_data.csv. Like λ8 it deletes its own rows from the database first and relies on the downstream chain to restore them.

λ10 (sprinklr-custom-updates) applies post-hoc corrections from four sources: a Google Sheet of per-metric fixes (only rows with a blank "Updated Date" are processed), a bulk MBS impressions file, a LinkedIn impressions replacement file, and a list of X quote-posts to delete. Impression changes automatically cascade into the derived rate columns. Everything is written to a full before/after audit log in S3. λ10 also builds and maintains permalink_registry — resolving Instagram shortcodes, LinkedIn URNs, TikTok and YouTube IDs by regex and Facebook URLs through Apify — and runs a report-only duplicate monitor that never deletes.

λ11 (push_follower_database) loads weekly follower counts into follower_table, interpolating gaps and applying a hardcoded set of LinkedIn follower overrides for seven markets. The overrides exist because the weekly run would otherwise overwrite manual corrections every week.

13 · Complete filter-rule reference

Twenty-two numbered rules run across four stages. Every one writes the removed rows, with a filter_reason column, to filtered_posts/ — so "why is this post missing?" is always answerable from S3.

Terminology. We now say exclusion list (formerly called the blacklist) and allow list (formerly whitelist) throughout this documentation and in client-facing material. The underlying technical object names have not changed yet — the file is still blacklist/Blacklist.csv, the V1 audit table is still blacklist_table, and the V2 reference table is still ref.blacklist — so anyone reading code, S3 or SQL sees the same names as before. Renaming the V2 table to ref.exclusion_list is queued as part of the V2 build; the V1 names stay as they are until that pipeline is retired.

15 · Known failure modes

Schema mismatch. Sprinklr renames export fields without notice. Because λ1 validates against exact column names, any rename blocks ingestion until the mapping is patched. Seven renames occurred in three weeks during July–August 2026, one of which was reverted five days later. The correct fix is always to add the new name as an alias to the existing canonical name — never to rename downstream — because both spellings then work and a revert costs nothing. The mapping file only ever grows.

Silent failure. Lambdas 5, 6, 8, 9 and 11 catch their exceptions and return statusCode 500 in the response body rather than raising. Lambda records those invocations as successes, so CloudWatch error alarms never fire. Alerting overall is uneven: λ1, λ2b, λ7, λ8 and λ9 use SES email; λ10 uses SNS; only the Fargate merge posts to Slack; λ2a, λ2c, λ2d, λ3b, λ4, λ5, λ6 and λ11 have no alerting at all.

Memory. The merge holds the existing table, the new data and the concatenated result in memory simultaneously, then de-duplicates across 182 columns. It has already exceeded a 16 GB container once. Because a kernel OOM produces no Python exception, the symptom is silence on Slack, not an error.

Duplicate accumulation. Re-running a date already present in master_table.csv appends a second copy rather than de-duplicating, because the dedup only collapses byte-identical rows and the column mapping usually changed between the two runs. Always check the row counts per Pull Date before replaying anything, and replay sequentially, oldest first — the merge rewrites the whole file, so overlapping runs race.

Historical debris. Because λ7 only ever upserts, rows created under older pipeline rules stay in sprinklr_table for ever. Data-quality checks that scan the whole table therefore flag conditions the current pipeline can no longer produce, which is why the quality console distinguishes current from historic findings.

16 · Operator cheat-sheet

QuestionWhere to look
Why is this post missing from Tableau?Search filtered_posts/ by permalink, or use the Filtered Posts Console. If nothing matches, check the six undocumented drop paths in §14.
Did the pipeline run this week?The Pipeline Runs tab of the V1 Quality Console shows each stage's artefact and timing. No finalsql for the Monday means the chain did not complete.
Did a schema mismatch block ingestion?The λ1 validation email, and whether amazon_sprinklr_pull/fluency/ has a folder for the date. A healthy day validates 23 files.
Is a missing day actually lost?Usually not. Each pull is a rolling ~88-day window, so a later pull normally still contains the posts — only the daily metric snapshots are gone.
How do I correct a wrong metric?Add a row to the "Core: Custom Metrics Change" sheet with a blank Updated Date. λ10 applies it and writes a full before/after audit entry.
Where did the collab rows go?λ8 deletes them at the start of its run and only the downstream chain restores them. Its pre-delete backup is in backup_sprinklr_table/.
